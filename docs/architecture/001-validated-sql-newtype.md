# ADR-001: ValidatedSql newtype for SQL safety

## Status
Accepted

## Context
The agent executes arbitrary SQL generated by LLMs. Without proper validation, this creates significant security risks:
- SQL injection via malicious LLM output
- Accidental execution of destructive operations (DROP, DELETE, UPDATE)
- Access to unauthorized tables/columns
- System table access

The original code passed raw SQL strings directly to the database layer, making it impossible to enforce security policies at compile time.

## Decision
Introduce a `ValidatedSql` newtype wrapper around `String` that can only be constructed through the `SqlValidator`:

```rust
pub struct ValidatedSql(String);

impl ValidatedSql {
    pub fn parse(validator: &SqlValidator, sql: &str) -> Result<Self, ValidationBlocked>;
    pub fn as_str(&self) -> &str;
    pub fn into_string(self) -> String;
}
```

The `DatabaseRepository::execute_read` method now only accepts `ValidatedSql` by value:

```rust
async fn execute_read(&self, sql: ValidatedSql) -> Result<QueryResult>;
```

## Consequences

### Positive
- **Compile-time guarantee**: Only validated SQL can reach the database layer
- **Single security seam**: All validation logic centralized in `SqlValidator`
- **Type-driven security**: Impossible to bypass validation accidentally
- **Testability**: Can inject mock `ValidatedSql` for unit tests

### Negative
- **Slight ergonomic cost**: Call sites must use `ValidatedSql::parse()` or the `execute_read_tool` helper
- **Migration effort**: Required updating all call sites to use the new type

## Alternatives Considered
1. **Runtime validation only**: Kept raw strings, validated at execution time. Rejected - no compile-time guarantees.
2. **Macro-based validation**: Use procedural macros to validate SQL at compile time. Rejected - SQL is dynamic (from LLM).
3. **Wrapper in database layer only**: Validate inside `SqlServer::execute_read`. Rejected - validation logic would be coupled to implementation.
